The "Analysis Paralysis" Challenge

Steam libraries are notorious for becoming digital graveyards. Users buy games during sales but never play them, leading to decision fatigue. Existing tools are just glorified spreadsheets. I wanted to build an intelligent assistant that helps users actually play their games by setting concrete goals. I didn't want a static UI; I wanted a conversational interface where users could ask, "What should I play that takes less than 10 hours?" and get an immediate, data-backed answer.

Architecture: The "Translator" Pattern

Most AI apps just pass user text to a chatbot. I architected a system that translates natural language into structured database queries.

  • The Translation Layer (llm_translator.py): I engineered a custom system prompt for Llama 3 that teaches it my specific GraphQL schema. I used "few-shot learning" within the prompt to show the model how to convert vague requests like "show me short games" into precise filters like average_playtime: { lt: 600 }.
  • The API (schema.py & resolvers.py): Instead of rigid REST endpoints, I built a flexible GraphQL API using Ariadne. This allows the frontend to request exactly the data it needs—whether that's just a game title or a nested tree of games, goals, and completion statuses—in a single network request.
  • The Database: I used MongoDB to handle the nested relationships. My resolvers use complex aggregation pipelines to join user data with global game metadata, allowing for queries like "Show me RPGs I haven't played yet."

Engineering Conversational State

A major challenge with LLMs is handling multi-turn conversations (like setting a specific goal).

  • State Management: In streamlit_app.py, I built a custom state machine to track where the user is in a conversation flow (e.g., SET_GOAL_AWAIT_GAME → SET_GOAL_AWAIT_HOURS → SET_GOAL_AWAIT_DEADLINE).
  • Hybrid Processing: The app intelligently switches between the LLM (for understanding intent) and deterministic logic (for executing database writes). If the LLM detects a "Set Goal" intent, my code takes over to guide the user through the required form fields, ensuring data integrity.

The PMM Takeaway

This project proves I understand the "Last Mile" of AI product development. It is easy to make a demo that chats; it is hard to make an AI that reliably interacts with a proprietary database. I understand how to design schemas for AI consumption, how to manage context in a stateless API, and how to bridge the gap between unstructured user intent and structured business logic.

The "No Frameworks" Challenge

In modern AI, anyone can import PyTorch, copy-paste a ResNet architecture, and hit 95% accuracy in an hour. But that doesn't mean they understand how it works. I wanted to prove I understood the math, not just the API. I imposed a strict constraint: Build a Deep Convolutional Neural Network using nothing but Python and NumPy.

The Engineering & Mathematics

  • Manual Backpropagation: I didn't use distinct autograd engines. I derived the gradients for every single layer (Convolution, Max Pooling, ReLU, Softmax) using multivariate calculus and implemented the backward pass by hand.
  • Solving the "Black Box": When a model failed to converge, I couldn't blame the library. I had to debug the flow of gradients myself. I built a numerical gradient checker to verify my calculus against the code, ensuring accuracy within 1e-7.
  • Performance Optimization: Python loops are too slow for image processing. I implemented the im2col algorithm to flatten image matrices, converting slow convolution operations into highly optimized matrix multiplications. This sped up training by over 100x.

Why 72% Is A Win

Without modern optimizers, pre-trained weights, or GPU acceleration, training a network from scratch is brutal.

  • Random Guessing: 10%
  • Linear Classifier: ~40%
  • My NumPy Implementation: 72%

I successfully beat the statistical baseline by nearly 2x using an architecture I built entirely from first principles.

The PMM Takeaway

When engineers talk about "vanishing gradients," "learning rate decay," or "architectural tradeoffs," I don't just nod along. I've faced those exact problems in raw code. I can translate deep technical constraints into clear product narratives because I've actually built the product from the math up.

The "LLM or Bust" Challenge

In the current AI hype cycle, the default answer to every problem is "use an LLM." But for high-volume tasks like real-time content moderation, calling GPT-4 for every single comment is prohibitively expensive and slow. I wanted to quantify the tradeoff. I built a sarcasm detection system to answer a specific business question: Can a specialized, lightweight model replace a massive generalist LLM?

The Experiment

I designed a head-to-head comparison using a sarcastic news headlines dataset.

  • The Heavyweight: I prompted GPT-3.5/4 with few-shot examples.
  • The Contender: I built and trained a custom Bi-Directional LSTM (RNN) using TensorFlow and GloVe embeddings.
  • The Goal: Measure the exact ROI of swapping a "smart" model for a "fast" one.

What I Found (The Data)

  • Accuracy: The LLM had a slight edge (~5% better), mostly on detecting sarcasm that required obscure pop-culture knowledge.
  • Speed: The traditional LSTM was 10x faster at inference. It ran locally and deterministically, while the LLM required variable-latency API calls.
  • Cost: Processing 1 million headlines with GPT-4 would cost thousands of dollars. The LSTM inference cost is negligible (electricity only) once trained.

The "Build vs. Buy" Verdict

The answer isn't "LLMs are better." The answer is "It depends on your constraints." If you need maximum accuracy for low-volume tasks, buy the LLM API. If you need real-time speed for high-volume processing (like chat moderation) and want to protect your margins, build the custom LSTM.

The PMM Takeaway

This project taught me how to perform a technical cost-benefit analysis. As a PMM, I don't just advocate for the "smartest" technology; I advocate for the right tool for the business case. I can look at a product roadmap and help engineering decide where we need "intelligence" (LLMs) and where we just need "pattern recognition" (Traditional ML) to solve the user's problem profitably.

The Design Challenge

Most portfolios are static Squarespace templates. I wanted to build something that proved I could actually ship a product. My goal was to recreate a fully functional, retro operating system inside the browser. The catch? I forced myself to use zero frameworks. No React, no Vue, no libraries for the UI. Just raw HTML, CSS, and JavaScript.

The Engineering: Building an OS in the Browser

  • Window Management System: Without React's state management, I had to build my own engine to handle window layering. I wrote the logic for dragging, minimizing, maximizing, and updating z-index values dynamically so the active window always stays on top.
  • Audio Engine: The music player isn't just an embed. I used the jsmediatags library to parse raw MP3 binary data directly in the browser, extracting and rendering the album art and metadata in real-time.
  • State Management: I built a lightweight, custom state store to track which applications are open, active, or minimized, ensuring the "taskbar" stays in sync with the desktop environment.

Visual Polish & UX

I didn't just want it to work; I wanted it to feel authentic.

  • Pixel Art: I hand-crafted the icons using CSS and Canvas to match the retro aesthetic.
  • Interactivity: Every button press and window drag has deliberate feedback.
  • Responsiveness: I engineered the CSS grid to adapt the desktop layout seamlessly from ultra-wide monitors down to mobile screens.

The PMM Takeaway

In product marketing, the difference between "good" and "great" is often in the last 10% of fit-and-finish. This project proves I obsess over the details. I understand the engineering effort required to make an interface feel "snappy," and I can speak the same language as frontend developers when we're discussing UI/UX tradeoffs.
